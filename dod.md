# Definition of Done (DoD) & Agent Architecture Guide

## 1. Обзор проекта (Project Overview)

**Smart Support Dispatcher** — высокопроизводительный сервис автоматической классификации и маршрутизации входящих обращений технической поддержки.

Система построена по двухуровневому паттерну **System 1 (Быстрый фильтр) + System 2 (Глубокий анализ)**:
* **System 1 (Fast-Path):** Локальная не-авторегрессионная модель на базе библиотеки [`laya`](https://github.com/NandhaKishorM/laya) (чекпоинт `laya-multilingual`, т.к. обращения на русском языке). Выполняет детерминированную классификацию за один прямой проход (p95 ≤ 50 мс на GPU, ≤ 300 мс на CPU) с расчётом калиброванного скора уверенности (`answer_confidence`).
* **System 2 (Deep-Path / Fallback):** Внешняя LLM (Gemini API через Google GenAI SDK, модель задаётся переменной `GEMINI_MODEL`). Подключается только в случаях низкой уверенности System 1, срабатывания механизма воздержания (`abstention`), мультидокументного контекста или противоречивых данных. Возвращает только структурированный ответ (`response_schema` на базе Pydantic-модели, категория — строго из enum таксономии).

## 2. Архитектура и поток данных (Architecture Flow)

```text
[Входящий тикет: API / Webhook]
                │
                ▼
┌──────────────────────────────────────┐
│  Validation & Preprocessing          │  <-- Очистка текста, Pydantic-валидация,
└──────────────┬───────────────────────┘      дедупликация по ticket_id
               │
               ▼
┌──────────────────────────────────────┐
│  Laya Classifier Engine (System 1)   │  <-- Single forward-pass классификация
└──────────────┬───────────────────────┘      (model="multilingual")
               │
     answer_confidence >= LAYA_MIN_CONFIDENCE (по умолчанию 0.85)
     и abstention == "passed" ?
               │
               ├── ДА ──► [Маршрутизация в очередь (Service Desk / Webhook)]
               │
               └── НЕТ (воздержание / низкая уверенность / неоднозначность)
               │
               ▼
┌──────────────────────────────────────┐
│  Gemini Fallback Agent (System 2)    │  <-- Chain-of-Thought, структурированный
└──────────────┬───────────────────────┘      ответ, черновик ответа пользователю
               │
     Ответ валиден по схеме, категория из таксономии
     и confidence >= GEMINI_MIN_CONFIDENCE ?
               │
               ├── ДА ──► [Маршрутизация в очередь (Service Desk / Webhook)]
               │
               └── НЕТ / System 2 недоступна / Circuit Breaker открыт
                          │
                          ▼
┌──────────────────────────────────────┐
│  Human-in-the-Loop / Manual Review   │  <-- Очередь ручной модерации
└──────────────┬───────────────────────┘      (статус PENDING_MANUAL_REVIEW)
               │
               ▼
[Исправленная разметка → датасет для дообучения и перекалибровки System 1]
```

### Ключевые категории (Default Taxonomy)
1. `SED`: проблемы с системой электронного документооборота (входящие, исходящие, служебные письма).
2. `DKA`: проблемы с кадровыми процессами (приказы, отпуска, командировки, штатное расписание, личные дела, документы кадрового делопроизводства).
3. `TECHNICAL_BUG`: ошибки сервиса, 5xx-ошибки, баги интерфейса, сбои синхронизации, не относящиеся к СЭД или кадровым процессам.
4. `FEATURE_REQUEST`: предложения по доработке, запросы нового функционала.
5. `GENERAL_INQUIRY`: общие вопросы, консультации, не требующие инженерного вмешательства.
6. `OTHER`: обращение не подходит ни под одну категорию (всегда уходит на ручную проверку).

**Правило приоритета при пересечении:** предметная область важнее типа проблемы. Ошибка в СЭД → `SED`, ошибка в кадровом модуле → `DKA`; `TECHNICAL_BUG` — только для остальных сервисов. Описания категорий для Laya (`criteria`) и для Gemini (enum + описание в промпте) берутся из одного источника конфигурации.

### Контракт ответа API
Каждый ответ эндпоинта классификации содержит поля:
`ticket_id`, `category`, `confidence`, `source` (`system1` | `system2` | `manual`), `status` (`ROUTED` | `PENDING_MANUAL_REVIEW`), `trace_id`, `model_version`.

## 3. Требования к кодовой базе (Engineering Standards)

Любой агент или разработчик, вносящий изменения, обязан соблюдать следующие стандарты:

1. **Окружение:** Python ≥ 3.10 (требование `laya`), зависимости зафиксированы lock-файлом (`uv.lock` или аналог). Версия `laya` закреплена (`laya==0.3.x`), ревизия чекпоинта — через `LAYA_REVISION`.
2. **Типизация:** 100% строгая статическая типизация с использованием `Pydantic v2` и Python `type hints`. Для сторонних библиотек без типов (`torch`, `laya`) допускаются только явные overrides в `pyproject.toml` (`ignore_missing_imports`), без `# type: ignore` в коде.
3. **Асинхронность:** Все I/O операции (сетевые запросы, обращение к БД/Redis, вызовы внешних API) должны быть полностью асинхронными (`async/await`). Инференс Laya изолирован в `run_in_executor` или отдельном воркере, чтобы не блокировать event loop FastAPI; число одновременных инференсов ограничено (`asyncio.Semaphore`, `LAYA_MAX_CONCURRENCY`).
4. **Отказоустойчивость (Circuit Breaker & Retries):**
   * Таймаут одного вызова Gemini API — 3.5 с, до 2 повторов с экспоненциальной задержкой; общий бюджет System 2 на тикет — не более 10 с.
   * Circuit Breaker: после 5 ошибок подряд вызовы System 2 приостанавливаются на 30 с (параметры вынесены в конфигурацию).
   * Если System 2 недоступна или Circuit Breaker открыт, тикет автоматически получает статус `PENDING_MANUAL_REVIEW`, сервис не должен падать с 500.
5. **Конфигурация:** Все параметры (пороги уверенности, API-ключи, таймауты, списки и описания категорий, модель Gemini) загружаются исключительно через `BaseSettings` (`pydantic-settings`) из переменных окружения. Никакого хардкода.
6. **Защита данных:** Перед отправкой в System 2 персональные данные (ФИО, табельные номера, телефоны, email, паспортные данные, СНИЛС) маскируются. Исходный текст обращений не пишется в логи (логируются только `ticket_id`, `trace_id`, категория и метрики).
7. **Observability:**
   * Каждый запрос имеет сквозной `correlation_id` / `trace_id`.
   * Время отклика логируется раздельно для System 1 и System 2.
   * Экспортируются метрики Prometheus: доля обращений в System 2 (fallback rate), доля воздержаний, распределение по категориям, расход токенов Gemini, латентность p50/p95 по этапам.
   * Эндпоинты `/health` (liveness) и `/ready` (readiness: модель загружена и прогрета тестовым запросом).

## 4. Definition of Done (Критерии завершения задачи)

Задача считается выполненной (**DONE**) только при одновременном соблюдении следующих условий:

### 1. Качество кода и типизация
- [ ] Отсутствуют синтаксические и стилевые ошибки (пройдены `ruff check .` и `ruff format --check .`).
- [ ] Пройдена строгая статическая проверка типов (`mypy --strict src/` без ошибок).
- [ ] Все публичные классы и методы имеют лаконичные docstrings (правила `D` в `ruff`).

### 2. Тестирование
- [ ] **Unit-тесты:** все изолированные компоненты (мапперы, калибровка скоров, парсеры, PII-маскирование, валидация ответа Gemini) покрыты тестами (`pytest`).
- [ ] **Интеграционные тесты:**
  - Протестирован сценарий быстрого пути (`answer_confidence >= threshold`).
  - Протестирован сценарий перехода в fallback (`answer_confidence < threshold` или `abstention == "abstained"` → Gemini).
  - Протестирован сценарий невалидного ответа Gemini (категория вне таксономии / нарушение схемы → ручная проверка).
  - Протестирован сценарий отказа внешнего LLM API и открытия Circuit Breaker (graceful degradation).
  - Протестирована дедупликация повторных вебхуков с тем же `ticket_id`.
- [ ] В CI нет реальных обращений к внешним сервисам: Gemini подменяется моками (`respx` / фейковый клиент), Laya — фейковым классификатором (реальная модель — только в отдельном маркере `@pytest.mark.model`).
- [ ] Покрытие кода тестами не ниже **85%** (`pytest --cov=src --cov-fail-under=85`).

### 3. Качество модели (ML Quality)
- [ ] Зафиксирован размеченный тестовый набор (≥ 50 тикетов на категорию), не пересекающийся с данными для дообучения и калибровки.
- [ ] Macro-F1 System 1 на тестовом наборе ≥ **0.85**; к отчёту приложена матрица ошибок.
- [ ] Калибровка: ECE ≤ **0.05** (temperature scaling / `fit_binning_map` из Laya).
- [ ] Доля обращений, уходящих в System 2, ≤ **30%** при точности ≥ **0.95** на тикетах, принятых System 1.
- [ ] Порог `LAYA_MIN_CONFIDENCE` подобран на валидационной выборке (кривая selective accuracy / coverage), а не задан вручную.
- [ ] Отчёт оценки воспроизводим одной командой (фиксированный seed, версия `laya`, ревизия чекпоинта, хэш датасета).

### 4. Производительность и ресурсы
- [ ] Латентность System 1 при `batch_size=1` и тексте до 512 токенов: p95 ≤ **300 мс** (CPU) или ≤ **50 мс** (GPU); замер не менее чем на 200 запросах после прогрева, железо указано в отчёте.
- [ ] Модели Laya загружаются в память один раз при старте приложения (через FastAPI `lifespan`) и прогреваются тестовым запросом, а не на каждый HTTP-запрос.
- [ ] Отсутствуют утечки памяти: прирост RSS процесса ≤ **50 МБ** за 1000 последовательных запросов после прогрева.

### 5. Безопасность
- [ ] Отсутствуют уязвимости зависимостей (пройдена проверка `pip-audit`).
- [ ] Никаких секретов, токенов или паролей в кодовой базе (`.env` в `.gitignore`, проверка сканером секретов, например `gitleaks`).
- [ ] Персональные данные маскируются до отправки в System 2 (покрыто тестами на реальных шаблонах обращений `DKA`).
- [ ] Защита от Prompt Injection: текст обращения передаётся в промпт изолированно (разделители, отдельная роль), ответ System 2 валидируется по схеме, категория вне таксономии отклоняется.

### 6. Документация и развёртывание
- [ ] Актуализирован `README.md` и API-документация (Swagger/OpenAPI по адресу `/docs`).
- [ ] При добавлении новых переменных окружения обновлён файл `.env.example`.
- [ ] Docker-образ собирается без ошибок (`docker build -t support-dispatcher .`); веса модели встроены в образ или подключаются томом, в проде задан `HF_HUB_OFFLINE=1`.
- [ ] Контейнер проходит `/ready` после старта (healthcheck в `Dockerfile` / `docker-compose.yml`).
